## (b) Findings by severity

### Medium (changes the generality or wording of a conclusion; no number flips)

**F1 — Spot req/$ advantage is a us-central1 artefact.** `g4_vs_v6e_comparison.md` §5 itself lists us-east5 spot: G4 $17.95/8 = $2.24, v6e $12.96/8 = **$1.62** per accelerator-hour (2.5× the us-central1 spot price). With those prices the v6e spot req/$ ratios become 0.95 / 0.89 / 0.99 / 0.86 / 1.12 (p50-70 / p99-110 / Poisson / p90<500 / saturation) — parity or G4 ahead. The v6e run physically happened in us-east5. On-demand us-east5 for v6e is not in §5, so that column cannot be checked. The reports say "us-central1 list, like the rest of the comparison", which is consistent, but the sentence "1.65–1.9× better on spot" must carry the region. Evidence: `scratch/qc_price.out`.

**F2 — "G4 without fast-prefill ≈ 116 req/s, below v6e's 132" is not supported at that operating point.** 1.66× is the synthetic A/B ratio at saturation (c = 64: 136.8 / 82.3). The same `verify_summary.md` gives 1.48× at c = 8 (108.2 / 73.2) and 1.54× at c = 16 (120.4 / 78.3) — the regime where p50 = 70 ms sits (c ≈ 14). 192 / 1.48–1.54 = 125–130, and the real prompts have 256 computed tokens vs 465 synthetic, which dilutes the prefill saving further. Honest statement: "≈ 115–130, i.e. roughly at parity with the v6e chip's 132", not "below". The tie-back supports "v6e ≥ G4 without fast-prefill" only at saturation (88–116 vs 82). A ~15-minute G4 run with the flag removed (one server start, c = 8/12/16 × 60 s) would settle it; I am not recommending it unless the "software not silicon" box is going to be quoted to the customer. Evidence: `g4/verify/verify_summary.md` A/B tables; `tieback/`.

**F3 — TPU utilization telemetry exists and was ignored.** `tpu_info.log` reports chip-0 duty cycle and TensorCore utilization in 1217 of 1265 snapshots (first ~50 are N/A before the engine attached). Per measured window: c=1 duty 67 % / TC 27 %; c=4 89 / 44; **c=8 95 / 58.5**; c=16 90 / 61; c=48 96 / 64; c=64 **99.7 / 66.1**; c=128 96 / 64; c=256 99 / 62–66; soak_125 90 / 53. `env.txt` shows `TPU_RUNTIME_METRICS_PORTS=8431…` was set, so the "needs the runtime metrics port" explanation is wrong. Consequence: the chip-bound reading is *measured*, not inferred (duty ≥ 90 % from c = 8 on, host 0.3 % busy); and TC utilization is flat at 64–66 % from c = 32 to c = 256 while throughput goes 139 → 201, which quantifies the padding / non-MXU share the report hypothesises. This strengthens the report; it is listed as medium only because two documents assert the opposite. Evidence: `scratch/qc_tpuinfo.out`.

### Low (text accuracy; explanations)

**F4 — v6e c = 64 is a deterministic scheduler resonance, not noise.** Per-10-s throughput inside the window is flat (129–134 req/s), 76 % of latencies sit in one 25-ms bucket (500–525 ms), and `running` oscillates 35/18/11. 64 × ~257 computed tokens (353 × (1 − 0.272)) = 16.4 k > `--max-num-batched-tokens 16384`, while 63 × 257 = 16.2 k fits: the batch splits 63 + 1 and the 1-request step is padded to a bucket, giving ~513 ms per round → 64 / 0.513 = 125 req/s. c=48 (12.3 k tokens, one step, 314 ms) and c=128 (two full steps, 659 ms) do not split. The same mechanism explains the Poisson cliff (p50 136 → 644 ms between 140 and 160 req/s) and the `V1_nofp` c=128 gap (both windows internally flat; different steady state: running 49/56/28 vs 64). This is a deployment-relevant caveat (a customer at ~60 in flight hits it), and it means every v6e point at c ≥ 48 carries ±10–15 % state dependence. Evidence: `scratch/qc_anomaly.out`, `samples/conc_c64.csv`, `conc_c64_gauges.csv`, `server_V1_bs32.log:16` (max_num_batched_tokens).

**F5 — "Max with p90 < 500" row mixes rules.** G4 246 is an interpolation (c = 96 → 128), v6e 152 is the best measured point. Same rule for both: best point 243 vs 152 → 1.60× speed, 1.04× / 1.67× req/$ (no change at 2 dp elsewhere). Also, the v6e 152 is the crest of a jagged curve (c=32 139, c=64 131); with either neighbour the on-demand ratio is 0.90–0.95×, i.e. this row's "parity" is one 60-s window wide.

**F6 — G4 p99 = 110 readout is host/window-sensitive.** Run 1 gives 207.8; run 2's three cross-check points give 190.5 (c=16 p99 = 110.7 ms there). The 1.56× in that row could be 1.43×. Worth one clause.

**F7 — 30,006 `WARNING [tpu_runner.py:1634] Should not schedule a request that does nothing!` lines in `server_V1_bs32.log`** (5,282 in nofp, 1,395 in bs256), unreported. Concentrated at c=1 (~2,000/min), c=4, c=16–64, rate_100–140 and the soak (~900/min); near zero at c=8, 12, 96–256 and rate ≥ 160. No correlation with throughput (c=8 and c=16 have ≈0 vs 1,200/min and the same 132–140 req/s), 0 errors, top1 = label 100 %. Looks like empty scheduler iterations; should be mentioned and raised upstream with the `allowed_token_ids` bug.

**F8 — `allowed_token_ids` crash has no on-disk evidence.** Run-1's server log was copied before the smoke test; the traceback exists only in the transcript. The deviation itself is fine (see verdict), but the report's §8 row for run 1 ("dataset profile and the start-up logs") is also wrong: no `dataset_stats.json`, `prep.log` empty. Side note: `env | grep -v -i token` in the driver filters `GDM_NO_ALLOWED_TOKEN_IDS` out of `env.txt`; `progress.log:1` (`allowed_token_ids=0`) and the driver order (export at line 90, server start later) show it was set.

**F9 — Minor number/wording errors:** start-up 25/22 min → 21.7/18.0 min (F in table row 35); README "390k" (row 30); bs256 "15–28 %" → "4–28 %" (row 24); nofp omits c=128 (row 23); "API server idle" → 0.2–0.45 cores (row 31); cross-check "±5–10 %" → "−5…+11 %" (row 13); v6e README intro says the run was on a `ct6e-standard-1t` (44 vCPU, 176 GB) and three paragraphs later says 4t; AUC ranges 0.61–0.64 on both; comparison §8 "82 vs 88–116 … close" holds at c=64 (82 vs 88) but at c=128 v6e is 116 vs 82.

## (e) Is the 1:1 comparison fair?

**Yes for speed; yes with two caveats for cost.**

* **`allowed_token_ids` (§3.1):** fair. Same score definition on both; top-1 was Safe/Un on 100.0000 % of requests on both, so the mask would not have changed any answer; on G4 the proper A/B (`--bypass-mw --no-allowed` vs `--bypass-mw`) measured nil (194.9 vs 198.3 req/s; 69.7 vs 72.0 ms). If anything the omission spares TPU a trivial sampler op. The crash itself is unverifiable from disk.
* **Block size (§3.2):** fair. Effective 32-token prefix-cache granularity on both (G4 via the hybrid lcm, TPU forced), identical 27.2–27.3 % hit rate and identical 6.4 % on the tie-back; the TPU default would have been *unfair to TPU* and was measured and reported separately.
* **Host (§3.7):** fair. One device, pinned, other chips unattached for the whole run, host 0.3–0.4 % busy, no CPU limits on either pod, same in-pod load generator at ≤ 0.06 cores; the accelerator is the limiter on both (G4 util 91–100 % at 600 W; v6e duty 90–100 %, TC 58–66 %).
* **Prices (§3.8):** arithmetic correct; the two stated assumptions (1-accelerator shape = ⅛ node, us-central1 list) are reasonable, but the spot conclusion must carry the region (F1) and the p90 < 500 row should not be used to argue on-demand parity (F5).
* **Fast-prefill attribution (§3.12):** the mechanism is plausible and the no-op is measured at c ≤ 64, but "G4 without fast-prefill would be below v6e" is not established; "about equal" is what the data supports (F2).

Headline conclusions that stand as written: G4 192 / 208 req/s at the customer's SLOs vs v6e 132 / 133; G4 1.4–1.6× faster per accelerator; one v6e chip does not meet the 190–240 band; on-demand req/$ roughly at parity (1.04–1.19×) at us-central1 list.
